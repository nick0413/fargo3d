## 1. Sharing — what stops another person installing this fork

The C build is not the problem. A machine with a normal CUDA toolkit and a working `g++` runs
`make SETUP=fargo PARALLEL=0 GPU=1 BIGMEM=1` and gets `./fargo3d`. Our two new source files include
only `fargo3d.h` and standard headers, contain no absolute paths, and sit in `MAINOBJ` as plain CPU
objects, so they add no dependency. What breaks is everything around the binary.

## 2. Physics — recorded now, fixed later

Both defects sit in `src/accretion.c`. Both are latent in practice: `planets/jupiter.cfg` sets
`Accretion 0.0`, and `acc_apply()` returns early when no planet has a positive rate, so the shipped
run never reaches the code. They matter the moment the sink is switched on.

### P-1. The momentum transfer credits the accreted mass twice

`src/accretion.c:180-182`

```c
Sys->mass[p] += dm;
Sys->vx[p] += dpx / Sys->mass[p];
Sys->vy[p] += dpy / Sys->mass[p];
```

`dpx` and `dpy` accumulate `frac * rho * Vol * vx`, which is exactly the momentum the removed gas
carried. So the planet receives `dm` of mass and `dp` of momentum, and its new momentum should be:

```
correct:  p_new = m*v + dp          =>  v_new = (m*v + dp) / (m + dm)
today:    p_new = m*v + dm*v + dp   =>  v_new = v + dp / (m + dm)
```

The excess is the term `dm*v`: the accreted mass is credited once as mass already moving at the
planet's velocity, and again through the gas's own momentum. It is not a rounding difference. In the
400-step run recorded on 2026-10-28 the planet accreted `m_acc ≈ 5.2e-5` against `m = 1e-3`, so the
spurious momentum is about 5% of the planet's momentum, and it always points along the planet's
current velocity. A bias in a fixed direction does not average out of a migration measurement.

Fix: `v_new = (m*v + dp) / (m + dm)`, computed before the mass is overwritten.

**Proof that fails without the fix:** with the sink on and no other force acting, the total linear
momentum of gas plus planet must be conserved. Sum it from the field before and after one
application; today the sum grows by `dm*v`.

### P-2. The angular-momentum check cannot fail

`src/accretion.c:175-190`

```c
real booking = xp * (dm * vpy + dpy) - yp * (dm * vpx + dpx);
real l_before = mp * (xp*vpy - yp*vpx);
...  apply the velocity update ...
l_after = Sys->mass[p] * (x*vy - y*vx);
e = fabs((l_after - l_before) - booking);
```

Substitute the update into `l_after` and the difference reduces to the booking expression exactly:

```
l_after - l_before = dm*(x*vy - y*vx) + x*dpy - y*dpx
                   = x*(dm*vy + dpy) - y*(dm*vx + dpx)   ==  booking
```

So `max_L_err` sits at machine precision by construction, whatever the transfer does. The reported
`dL_planet == L_sink` to 1e-15 measures arithmetic, not conservation. The earlier note claiming this
as a tight physical check was wrong and is corrected here.

Fix: compare against an observable computed from the state and the field, not from the same
expressions used to apply the change — for example L(gas, before) − L(gas, after) against
L(planet, after) − L(planet, before), plus the angular momentum that crosses the domain edge.

wrong at `PARALLEL=1`.

| M-2 | `src/control.c` (header) | The frame has no rank field, and each rank emits only its own slab, so a parallel stream is one slice of the grid presented as the whole grid. | OPEN |

## 6. Facts established while reviewing

Recorded so they are not re-derived, each one read from the tree or the filesystem during this pass.

- The binary in the tree (`fargo3d`, 2026-10-28 16:55:24) is newer than every source file, so it
  matches the committed code. `strings fargo3d` contains `FARGO_CONTROL_PORT`, `FARGO_ACCRETION` and
  `FARGO_ACCRETION_FRAC`, so the instrumentation is compiled in.
- `control.o` and `accretion.o` are in `MAINOBJ` only (`src/makefile:309`), never in `GPU_OBJ`, and
  they build through the generic rule `%.o : %.c ${GLOBAL}` (`src/makefile:672`). They are therefore
  CPU-only objects, never translated to `.cu`, and they do rebuild when the `.opt` changes.
- `setups/fargo/fargo.opt` is unmodified, so the build is float64. `REALTYPE` in a run's summary
  confirms it.
- `planets/jupiter.cfg` sets `Accretion 0.0`. `FARGO_ACCRETION=1` alone therefore changes nothing:
  the sink is inert until the cfg carries a positive rate.
- `tools/live/live_view.py` uses only the Python standard library. The web viewer needs Node and
  `npm install && vite build`; no lockfile is committed.
